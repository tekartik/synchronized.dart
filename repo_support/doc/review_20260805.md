### 1.3 CRITICAL PATH TRACE

**Transaction:** `await lock.synchronized(computation)` on the default `Lock()`.

**Why it is the highest-value one:** it *is* the product. Every other public entry point is a wrapper over this exact path — `Lock(reentrant: true)` delegates to it per nesting level (`reentrant_lock.dart:33`), `MultiLock` calls it once per underlying lock (`multi_lock.dart:40`), `Object.synchronized` calls it on a cached instance (`extension_impl.dart:36`), and `synchronizedSync` falls back to it (`lock_extension.dart:31`). If this path is wrong, everything downstream of the package — `dev_build` and every consumer of it — silently loses mutual exclusion.

The trace touches all four layers plus `dart:async`.

---

**Hop 1 — L1 public API: instance selection** · `lib/synchronized.dart:48-54`

```dart
factory Lock({bool reentrant = false}) {
  if (reentrant) {
    return ReentrantLock();
  } else {
    return BasicLock();
  }
}
```

*Transforms:* one bool → a concrete implementation. No validation needed, no state.
*Can fail:* nothing.
*Errors/cancellation/backpressure:* n/a.

---

**Hop 2 — L2 queue registration (the critical section of the critical section)** · `lib/src/basic_lock.dart:21-23`

```dart
final prev = last;
final completer = Completer<void>.sync();
last = completer.future;
```

*Transforms:* the lock's single-slot tail pointer. `prev` captures the predecessor; `last` immediately becomes this call's future. Because `synchronized` is `async` and there is no `await` before these three lines, they run **synchronously on the caller's stack** — this is what makes R4 ("if it is unlocked calling synchronized grab the lock") true, and it is asserted by `common_lock_test_.dart:338-343`.
*Can fail:* nothing throws here. The real hazard is ordering, not exceptions: if an `await` were ever introduced above line 21, two callers could both read `last == null` and run concurrently. There is **no test that would catch that regression directly** — `common_lock_test_.dart:338-343` only checks `locked` transitions, not the interleaving of two same-tick callers.
*Errors/cancellation/backpressure:* **no backpressure.** The queue is an unbounded chain of futures; 10 000 queued calls is exactly what `common_lock_test_.dart:101-106` does, and nothing rejects the 10 001st.

---

**Hop 3 — L2 → `dart:async`: wait for the predecessor** · `lib/src/basic_lock.dart:26-33`

```dart
if (prev != null) {
  if (timeout != null) {
    // This could throw a timeout error
    await prev.timeout(timeout);
  } else {
    await prev;
  }
}
```

*Transforms:* suspends until the predecessor's completer fires. `prev` is always an internal `Completer<void>.sync().future` that is only ever `complete()`d, never `completeError`ed — so `await prev` can only ever succeed or hang. That is why the caller's error never leaks into the next waiter (R5).
*Can fail:* `TimeoutException` from `Future.timeout` — surfaces to the user as a thrown `TimeoutException` with `computation` never invoked (R14). Verified end-to-end by `common_lock_test_.dart:135-150` and `issues_test.dart:12-29`.
*Errors/cancellation/backpressure:* **partial.** Timeout abandons the *wait*, and the `finally` at `:56-61` correctly re-serialises the abandoned slot. But a `timeout: null` caller waits forever with no cancellation token — the only escape is the timeout parameter. For `MultiLock` this hop runs once per lock, which is the source of the `N × timeout` defect (see BUG-05).

---

**Hop 4 — L2 computation invocation** · `lib/src/basic_lock.dart:36-41`

```dart
var result = func();
if (result is Future) {
  return await result;
} else {
  return result;
}
```

*Transforms:* runs the user's computation. The `is Future` branch is what makes the lock cover the *whole* async computation, not just its synchronous prefix.
*Can fail:* anything the user's code throws, sync or async. It propagates out through the `finally` (which does not swallow it — there is no `catch` anywhere in `lib/`), reaching the caller as a rejected `Future` (R5). Covered by `common_lock_test_.dart:236-290`.
*Errors/cancellation/backpressure:* **yes for errors** (`finally` releases the lock on the throwing path — `common_lock_test_.dart:248-252` asserts the lock is reusable after a throw). **No for cancellation:** a `timeout` that fires in Hop 3 never touches a computation that is already running. This is the exact hop `synchronizedSync` bypasses — `lock_extension.dart:28-30` returns `computation()` without ever reaching Hop 2, so when `T` is itself a `Future`, nothing awaits it and nothing holds the lock (BUG-02).

---

**Hop 5 — L2 release** · `lib/src/basic_lock.dart:42-64`

```dart
void complete() {
  // Only mark it unlocked when the last one complete
  if (identical(last, completer.future)) {
    last = null;
  }
  completer.complete();
}
if (prev != null && timeout != null) {
  // ignore: unawaited_futures
  prev.then((_) { complete(); });
} else {
  complete();
}
```

*Transforms:* clears the tail pointer **only if this call is still the tail** (`identical` guard), then wakes the successor. `Completer.sync()` means the successor resumes on this stack rather than a later microtask.
*Can fail:* `completer.complete()` on an already-completed completer would throw `StateError` — unreachable, because the two branches are mutually exclusive and each runs once. `prev.then(...)` has no `onError`, which would normally be an unhandled-async-error trap; it is safe **only** because of the Hop 3 invariant that `prev` never carries an error. That invariant is load-bearing and undocumented at this line.
*Errors/cancellation/backpressure:* **yes.** The timeout branch deliberately defers release until the predecessor finishes, preserving FIFO after an abandoned wait. `common_lock_test_.dart:152-197` covers it.

---

**Hop 6 — L2 reentrant variant: level resolution** · `lib/src/reentrant_lock.dart:22-31`

```dart
final level = innerLevel;                       // (Zone.current[this] as int?) ?? 0
if (level >= innerLocks.length) {
  throw StateError('This can happen if an inner synchronized block is spawned outside …');
}
final lock = innerLocks[level];
```

*Transforms:* the ambient `Zone` value into an index into the per-level lock stack.
*Can fail:* `StateError` when a stale zone outlives its block — a deliberate, well-messaged guard (R11), tested at `reentrant_lock_test.dart:231-249`.
*Errors/cancellation/backpressure:* yes for this path. **But the sibling accessor is not guarded:** `canLock` (`reentrant_lock.dart:63-68`) performs the same `innerLocks[innerLevel]` lookup with **no bounds check**, protected only by the `!locked ||` short-circuit. Verified: in a stale zone while the lock is still held, `lock.canLock` throws `RangeError (length): Invalid value: Not in inclusive range 0..1: 2` — and `lock.synchronizedSync(...)` throws the same, because it calls `canLock` first (BUG-04).

---

**Hop 7 — L2 reentrant variant: zone establishment** · `lib/src/reentrant_lock.dart:33-46`

```dart
return lock.synchronized(() async {
  innerLocks.add(BasicLock());
  try {
    var result = runZoned(() { return func(); }, zoneValues: {this: level + 1});
    …
  } finally {
    innerLocks.removeLast();
  }
}, timeout: timeout);
```

*Transforms:* pushes a level, runs the computation in a child zone carrying `level + 1`, pops on exit. Delegates all actual mutual exclusion back to Hop 2–5 on `innerLocks[level]`.
*Can fail:* the user's computation (same as Hop 4); `TimeoutException` from the delegated `BasicLock`.
*Errors/cancellation/backpressure:* yes — `finally` guarantees the pop. I specifically probed whether an **unawaited** inner block breaks the LIFO assumption and it does not (1.9.A).

---

**Hop 8 — L2 object-extension variant: global cache** · `lib/src/extension_impl.dart:34-48`

```dart
var lockImpl = objectMakeLock(monitor);
try {
  return await lockImpl.synchronized(() async { … }, timeout: timeout);
} finally {
  if (!lockImpl.locked) { cleanUpLock(monitor); }
}
```

*Transforms:* an arbitrary user object into a `BasicLock` held in a **process-global** `Map` (`utils.dart:8`), then removes it when the last holder leaves.
*Can fail:* the map is keyed by `==`/`hashCode`, so two unrelated libraries in the same app that both write `'lock'.synchronized(…)` or `42.synchronized(…)` share one global lock and will block each other with no diagnostic. At `5026925` the dartdoc claimed the opposite (identity); it has since been corrected to state `==`/`hashCode` and to warn about the process-global namespace.
*Errors/cancellation/backpressure:* yes for errors and cleanup. I expected a cache **leak** after a timeout and **verified there is none** (1.9.A) — the sync completer at Hop 5 closes that window.

### 1.9 ADVERSARIAL SELF-REVIEW

#### A. Three findings I suspected were shallow — re-investigated

**A1. "The object-extension cache leaks a `BasicLock` after a timeout."**
My static trace of `extension_impl.dart:44-47` said: caller B times out → B's `finally` sees `lockImpl.locked == true` (because `last` is B's completer) → no cleanup; then A finishes and *its* `finally` also sees `locked == true`; then B's deferred `complete()` clears `last` with nobody left to clean the map. I was going to file it as a P1 memory leak.

**I ran it.** Held `'leak-key'` for 200 ms, timed out a second caller at 10 ms, let everything settle, then inspected `cacheLocks`:

```
after all settled: cacheLocks=0 keys=[]
```

**Refuted.** My ordering was wrong. `basic_lock.dart:22` uses `Completer<void>.sync()`, so when A's `finally` calls `completer.complete()`, B's `prev.then((_) => complete())` callback (`:59-61`) fires **synchronously, inside A's `finally`, before A's `objectSynchronized` `finally` runs**. `last` is therefore already `null` when the cleanup check happens. The `.sync()` is load-bearing and I had treated it as incidental. Finding withdrawn; recorded in NOT FLAGGED.

**A2. "An unawaited inner reentrant block corrupts `innerLocks` via `removeLast()`."**
`reentrant_lock.dart:45` pops by position, not identity. If an outer block returns while an inner block it spawned is still running, the outer's `finally` pops the *inner's* lock and the stack desynchronises.

**I ran it** — an outer block that calls `lock.synchronized(asyncWork)` without awaiting or returning it:

```
after outer:          innerLocks=2  locked=true   order=[outer-start, inner-start, outer-end]
after inner settled:  innerLocks=1  locked=false  order=[outer-start, inner-start, outer-end, inner-end]
subsequent block ran=true innerLocks=1
```

**Refuted.** Depth returns to 1 and the lock is fully reusable. The stack is a depth *counter* that happens to be a list; since every push is matched by exactly one pop, the ordering of the pops does not matter for depth. The `BasicLock` objects popped are not the ones pushed by that frame, but no waiter is orphaned because the *level index* — not the object — is what callers resolve through (`reentrant_lock.dart:31`). Finding withdrawn.

**A3. "`ReentrantLock.canLock` throws `RangeError` in a stale zone."**
First probe **refuted** it: from a zone captured inside a completed block, `canLock` returned `true` cleanly, because `canLock = !locked || !_currentLevelLocked` (`:68`) short-circuits on `!locked` and never evaluates the indexing.

**I looked again** and constructed the case where `locked == true` *and* the zone level is stale — capture a zone at depth 2, let the inner block unwind, then evaluate from the still-running outer block:

```
inside outer: innerLocks=2 locked=true
  stale innerLevel=2
  canLock THREW: RangeError (length): Invalid value: Not in inclusive range 0..1: 2
  synchronizedSync THREW: RangeError (length): Invalid value: Not in inclusive range 0..1: 2
```

**Upgraded, and its blast radius grew.** The first probe was the shallow one. `synchronizedSync` inherits the throw because `lock_extension.dart:28` reads `canLock` first — so a *documented public getter* and a *documented public method* both throw a raw `RangeError` where `synchronized` would have thrown the deliberate, explanatory `StateError` from `reentrant_lock.dart:27-29`. Filed as BUG-04.

#### B. Three things I did not look for

1. **Web/WASM behavioural differences.** I ran only `dart test -p vm`. `dart_test.yaml` also declares `chrome` and `node` × `dart2js`/`dart2wasm`, and `Zone`/microtask semantics can differ under compilation. **Gap → OPEN QUESTIONS.** Two of my findings (BUG-04's zone staleness, and the `Completer.sync()` ordering that A1 depends on) are timing-sensitive enough that VM-only confirmation is not conclusive.
2. **Performance regression vs. the recorded 2019 baseline.** `doc/synchronized_development.md:41-51` records `syncd 6.28 s` / `13.59 s` for 500 000 ops at v2.1.0. `perf_test_.dart` is excluded from the default glob and I did not run it. **Safe to ignore for correctness**, but it means nothing in CI would catch an order-of-magnitude regression → noted in OPEN QUESTIONS.
3. **Downstream-consumer compatibility.** `dev_build` depends on `synchronized >=3.0.0+3 <5.0.0`, and it is `dev_build` that runs this repo's CI. I did not check whether any fix in this backlog would ripple into consumers. **Safe to ignore** — every fix I propose is additive or a defensive copy; none changes a signature. The one exception is the object-extension keying (Q2), whose *behavioural* fix would be breaking, which is why it is deferred to an open question rather than filed as a task.

#### C. One unverified architectural assumption — then checked

**Assumption:** "Dart is single-isolate and `synchronized` is `async`, so the check-then-act in `BasicLock.synchronized` (read `last`, then assign `last`) is atomic — no two callers can both observe an unlocked lock."

**Checked.** `basic_lock.dart:17-23`: the method is `async`, and Dart runs an `async` body **synchronously up to the first `await`**. Lines 21–23 contain no `await`, so the read-modify-write completes on the caller's stack before control can return to the event loop. Confirmed behaviourally by `common_lock_test_.dart:338-343` (`locked` is `true` immediately after calling with an async body) and by R4 holding in every suite.

**Result: the assumption holds — but it is undocumented and structurally fragile.** Adding any `await` above line 21 (say, a future `await someAsyncPolicyCheck()`) silently breaks mutual exclusion for the entire library, and **no existing test would fail** (see 1.7, Hop 2). That is the single most dangerous line-level invariant in the codebase and it carries no comment. Filed as TEST-05.

#### D. Steel-manning my top-severity finding

**Top finding as originally drafted: BUG-01, "`MultiLock` accepts a lazy `Iterable` and provides zero mutual exclusion" — drafted P0.** My harness passed `base.map((e) => Lock())` and got fully interleaved execution (`[a-start, b-start, b-end, a-end]`) versus correct serialisation with `.toList()`.

**The strongest case that the code is right and I am wrong:**
`MultiLock`'s contract is "a lock that acquires *these* locks together" (`multi_lock.dart:5-11`). An iterable that manufactures a **brand-new `Lock` on every iteration** does not denote a set of locks at all — it denotes nothing. My harness did not find a bug; it constructed a caller that asked the lock to protect a different resource each time it looked. Garbage in, garbage out. Every example in the README (`README.md:211-220`) and every use in the test suite (`lock_factory.dart:23`, `multi_lock_test.dart:20`) passes a list literal. And the realistic lazy shape — `owners.map((o) => o.lock)` over stable owners — is **idempotent**, returns the same `Lock` instances every iteration, and works perfectly.

**How much of that holds up:** most of it. **I am downgrading BUG-01 from P0 to P1** and restating it accurately: the defect is not "lazy iterables are broken", it is that **`MultiLock` stores an `Iterable` it iterates at least four times** (`:22`, `:25`, `:28`, `:47`) **with no defensive copy and no documentation of the idempotence requirement it silently depends on.** The failure is not loud — it is total, silent loss of exclusion in a mutex — so it stays P1 rather than P3, and the fix is one line (`_locks = List<Lock>.of(locks)`).

**Consequence:** with BUG-01 downgraded, **this audit has no P0.** That is the correct outcome. The library's core path (Hops 1–5) is genuinely sound: 88 green tests, zero analyzer issues, zero `TODO`s, zero swallowed exceptions, zero I/O in the library, and a load-bearing `Completer.sync()` design that survived two of my three attempts to break it. The defects that remain are concentrated in the three newest surfaces — `MultiLock` (3.3.0), `synchronizedSync` (3.4.0), and the `Object` extension's documented contract — which is exactly where you would expect them.

### BUG-02 ✅ DONE — `synchronizedSync` silently skips the lock when the computation returns a `Future`

| | |
|---|---|
| **Severity** | P1 |
| **Effort** | M |
| **Evidence** | `synchronized/lib/src/lock_extension.dart:24-34`, esp. `:28-30` |
| **Source Audit** | 1.2 Pass B/R5, 1.3 Hop 4 |
| **Confidence** | HIGH (verified) |
| **Depends On** | none |

**Why it matters.** The fast path returns `computation()` directly without ever touching `last`, so when `T` infers to a `Future`, the returned future runs entirely **outside** the lock. Verified: `lock.synchronizedSync(() => asyncWork())` reported `lock.locked == false` immediately afterwards, and a subsequent `lock.synchronized(…)` block ran to completion *before* the "protected" work finished (`order = [a-start, b]`). `Lock.synchronized` handles this correctly (`basic_lock.dart:37-40` awaits a `Future` result); the two methods differ by four characters in the name and by everything in behaviour. The slow path is inconsistent too: verified `synchronizedSync<Future<int>>` returns a runtime `Future<Future<int>>`. Secondary defect from the same lines: errors are delivered **synchronously** on the fast path and **as a rejected `Future`** on the slow path, so `try { … } catch` placement that works when the lock is busy fails when it is free.

**Execution plan.**
1. Decide the contract (see OPEN QUESTIONS Q1). Recommended: keep `synchronizedSync` sync-only and make misuse impossible to miss.
2. In `lib/src/lock_extension.dart`, add a guard on the fast path — capture `final result = computation();` and `assert(result is! Future, 'synchronizedSync computation must be synchronous; use synchronized() instead')` before returning. Assertions are free in release and loud in dev/test.
3. Normalise error delivery: document explicitly at `:24` that the fast path throws synchronously, or wrap the fast path in `try/catch` → `Future.error` if a uniform shape is preferred.

### BUG-05 ✅ DONE — `MultiLock` applies `timeout` per lock, so the caller's bound is `N × timeout`

| | |
|---|---|
| **Severity** | P2 |
| **Effort** | M |
| **Evidence** | `synchronized/lib/src/multi_lock.dart:40-43` passes the same `timeout` into each nested acquisition; contract stated at `synchronized/lib/synchronized.dart:56-62` |
| **Source Audit** | 1.2 Pass B/R3, 1.7 |
| **Confidence** | HIGH (verified) |
| **Depends On** | none |

**Why it matters.** `Lock.synchronized`'s documented contract is "waits at most that `Duration` to acquire the lock". `MultiLock` implements `Lock` and therefore inherits that contract, but restarts the clock for every underlying lock. Verified: a 2-lock `MultiLock` with `timeout: 200ms` threw `TimeoutException` after **355 ms**. With 5 locks the worst case is 5× the caller's stated bound — and `timeout` exists specifically as a deadlock escape hatch, so overshooting it defeats its only purpose. `multi_lock_test.dart:34-44` asserts only *that* it times out, never *when*, which is why this shipped.

**Execution plan.**
1. In `MultiLock.synchronized`, compute a deadline once: `final deadline = timeout == null ? null : DateTime.now().add(timeout);`.
2. In `runWithLocks`, pass the *remaining* budget to each acquisition (`deadline.difference(DateTime.now())`), throwing `TimeoutException` immediately if it is already non-positive.
3. Add a test asserting total elapsed time stays within `timeout` (plus a tolerance) for a 2-lock `MultiLock` where the first lock frees partway through.
4. Note the semantic change in `CHANGELOG.md`.

**Verification.** The reproducer times out at ~200 ms, not ~355 ms. `multi_lock_test.dart:34-44` still passes.

**Risk.** Callers who (perhaps unknowingly) depended on the longer effective budget will now see `TimeoutException` sooner. This is a behaviour change on a published API — ship it in a minor version with a CHANGELOG entry. Alternative if you prefer strict compatibility: leave the behaviour and document the multiplication at `multi_lock.dart:31` and in the README — downgrade to P3, effort S.

### ARCH-01 — `MultiLock`'s `every`-based state is self-contradictory and nonsensical when empty

| | |
|---|---|
| **Severity** | P2 |
| **Effort** | M |
| **Evidence** | `synchronized/lib/src/multi_lock.dart:22-28`; enshrined by `synchronized/test/multi_lock_test.dart:23-30`, `:64-72`, `:107-109` |
| **Source Audit** | 1.2 Pass A/R12, Pass B/R12 |
| **Confidence** | HIGH (verified) |
| **Depends On** | TEST-01 |

**Why it matters.** With `MultiLock(locks: [l1, l2])` and only `l1` held, verified state is `locked = false`, `canLock = false`, `inLock = false` — "this lock is not locked, and you cannot lock it." Any caller using `if (!lock.locked)` as a fast-path guard (the pattern the package's own examples show at `example/example.dart:57-63` and `example/browser/main.dart:82-88`) will conclude the lock is free and then block. With `locks: []` it is worse: verified `locked = true`, `canLock = true`, `inLock = true` simultaneously, forever. The README documents `every` (`README.md:184`, `:194`, `:204`) so this passes the letter of R12 — but the purpose of exposing state is that callers can act on it, and this state is not actionable. `multi_lock_test.dart:107-109` already carries the comment `// Not what we would expect but ok...`.

**Execution plan.**
1. Decide the semantics (OPEN QUESTIONS Q3). Recommended: `locked` and `inLock` become `any` (partially held ⇒ contended); `canLock` stays `every` (needs all). That makes `locked == false` imply `canLock == true`, which is what callers assume.
2. Change `multi_lock.dart:25-28` accordingly; update the three README paragraphs (`:180-204`).
3. Guard the empty case — `assert(locks.isNotEmpty)` in the constructor, or document that an empty `MultiLock` is a no-op that always reports unlocked.
4. Update `multi_lock_test.dart:23-30`, `:64-72`, `:100-113` to the new expectations and delete the "not what we would expect" comment.
5. CHANGELOG entry — this is an observable behaviour change on a published API.

**Verification.** New invariant test: for every reachable state, `locked == false` implies `canLock == true`. All suites green.

**Risk.** Behaviour change on `MultiLock.locked`/`inLock`. Since these are inspection-only (no internal code branches on them), blast radius is limited to consumer diagnostics. Land after TEST-01 so `MultiLock` is actually covered by the shared suite.

## 3. OPEN QUESTIONS

**Q1 — What is `synchronizedSync`'s intended contract when `T` is a `Future`?** (blocks BUG-02)
Three options: (a) assert/throw on a `Future` result — recommended, keeps the method honest; (b) await it and hold the lock, which makes `synchronizedSync` behave like `synchronized` and removes the reason for its existence; (c) document the current behaviour as intended. Only you can say whether any consumer already relies on the fast path returning immediately.

**Q2 — Should the object extension become truly identity-based?** (the doc half is already done)
The dartdoc has been corrected to describe the actual `==`/`hashCode` behaviour, which was doc-only and safe. The remaining question is whether the *behaviour* should change instead. Switching `cacheLocks` to an `identityHashCode`-keyed map (`HashMap<Object, BasicLock>(equals: identical, hashCode: identityHashCode)`) would honour the original documented intent, but it is **breaking**: `extension_lock_test.dart:30-39` and `:82-88` show at least the test suite depends on value equality, and any consumer locking on equal strings would silently stop being serialised. If you want the behavioural change, it belongs at 4.0.0 as its own task.

**Q3 — What should `MultiLock.locked` / `inLock` mean for a partial hold?** (blocks ARCH-01)
`any` (recommended — "contended"), `every` (status quo — "fully held"), or a new tri-state. The README currently documents `every`, so whichever you pick, the README moves with the code.

**Q4 — Is `Lock` intended as a public extension point?** (blocks ARCH-03)
If yes, additions must be major-version. If no, say so in the dartdoc now and consider `base`/`final` at 4.0.0. History (`canLock`/`inLock` added in 3.3.0) suggests "no" is the operating assumption already.

**Q5 — Are the `.agents/skills` symlinks meant to be committed?** (blocks DX-06)
They resolve only on your machine. If they are a local convenience, they should be gitignored.

**Q6 — Web/WASM confirmation of this audit's findings.** (from 1.9.B1)
Everything here was verified on `dart test -p vm` / `dart run` on the VM only. `dart_test.yaml` also targets `chrome` and `node` × `dart2js`/`dart2wasm`, where microtask and `Zone` scheduling can differ. Two results are timing-sensitive enough to warrant re-confirmation there before acting: **BUG-04**'s stale-zone reproducer, and the `Completer.sync()` synchronous-callback ordering that 1.9.A1 depends on (if it does not hold under `dart2wasm`, the `cacheLocks` leak I withdrew becomes real on the web). Suggested: land TEST-02's new tests, then run the full platform matrix once and compare.

**Q7 — Is there a performance-regression gate anywhere?** (from 1.9.B2)
`perf_test_.dart` is excluded from the default glob and its only baseline is a hand-pasted 2019 table at `doc/synchronized_development.md:41-51`. Nothing in CI would catch an order-of-magnitude regression. Is that acceptable, or should the scheduled Sunday CI run publish timings?

**Q8 — Should `test/` ship in the published archive?**
`dart pub publish --dry-run` shows all 10 test files in the 15 KB archive. Harmless at this size and arguably useful as documentation, but if you would rather not ship them, that is a `.pubignore` decision.

## 4. NOT FLAGGED

- **`cacheLocks` leak after a timeout** — I traced it statically and was convinced it leaked; the runtime check showed `cacheLocks` empty. `Completer<void>.sync()` (`basic_lock.dart:22`) makes the successor's release callback fire inside the predecessor's `finally`, before the cache-cleanup check. Withdrawn (1.9.A1). Re-open only if Q6 shows different ordering under `dart2wasm`.
- **`innerLocks.removeLast()` corrupting the reentrant stack when an inner block is unawaited** — verified to restore depth correctly and leave the lock reusable. Pops are count-based and every push has exactly one pop. Withdrawn (1.9.A2).
- **`MultiLock` leaking already-acquired locks when a later acquisition times out** — verified: after a mid-chain `TimeoutException`, `l1.locked == false` and `l1.canLock == true`. The nested `try/finally` chain unwinds correctly.
- **`prev.then(...)` at `basic_lock.dart:59-61` with no `onError`** — normally an unhandled-async-error trap, but `prev` is always an internal `Completer<void>.sync().future` that is only ever `complete()`d. Safe. Worth a one-line comment, not a task.
- **Check-then-act in `synchronizedSync` (`canLock` at `:28`, then `computation()` at `:29`)** — no `await` between them, so nothing can interleave in a single-isolate runtime. Correct as written.
- **The `if (result is Future) … else …` idiom duplicated across three files** — 3 sites, ~4 lines each, all trivially correct, no observed drift. Extracting a helper would add indirection to the hottest path for no measurable benefit.
- **Circular imports between `lib/synchronized.dart` and `lib/src/*.dart`** — structural and unavoidable: the interface must live in the public library and implementations must see it. Legal and idiomatic in Dart.
- **No cancellation plumbing anywhere** — inherent to a lock primitive; `timeout` bounds acquisition and that is documented accurately at `synchronized.dart:56-62`. Adding `CancelableOperation` would mean a `package:async` dependency, violating R7 for a problem nobody has reported.
- **Unbounded waiter queue** — no cap on queued `synchronized` calls. Intrinsic to a FIFO mutex; `perf_test_.dart` queues 500 000 deliberately. Bounding it would be a new feature, not a fix.
- **`Future<dynamic>? last` (`basic_lock.dart:8`)** — `dynamic` where `void` would do, but it is only ever `await`ed and identity-compared. Cosmetic; `strict-casts` passes.
- **`(Zone.current[this] as int?)` (`reentrant_lock.dart:14`)** — an unchecked cast, but the key is `this`, so only this class writes it. `strict-casts` clean.
- **Missing copyright headers on `lib/src/*.dart` and `lib/extension.dart`** — inconsistent with `lib/synchronized.dart:1-2` and every test file. Cosmetic; `LICENSE` covers the package.
- **`repo_support/analysis_options.yaml` being weaker than the package's** — deliberate and correct; it is an unpublished tool package.
- **`dev_build` (this repo's CI tool) depending on published `synchronized`** — a bootstrapping loop in principle, but CI resolves the *published* version from pub, not the local source, so there is no circularity in practice.
- **`common_lock_test_.dart` / `perf_test_.dart` trailing-underscore naming** — an intentional exclusion from the `*_test.dart` glob, working as designed.
- **`example/info_timing.dart` detecting Dart 1 vs Dart 2 async timing** — vestigial (Dart 1 is long gone) but harmless, self-contained, and analyzer-clean. Delete it if you are already touching `example/`.
